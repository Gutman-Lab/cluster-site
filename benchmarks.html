Benchmarks

The most useful thing about a heterogeneous cluster is that you can measure what each kind of hardware actually does under the same workload. This page carries two Ceph campaigns: a September 2026 baseline and a clean four-tier rerun on 22 November 2026 — three repetitions per test, median reported, on an idle cluster with zero recovery — plus the September TrueNAS fio work and the ZFS tuning story.

Methodology — November 2026 campaign

  • Workload: rados bench, 30 seconds per test, 16 concurrent threads, 3× replication (size 3, min_size 2), against the dedicated profile pools.
  • Statistics: 3 repetitions per test, median reported. All 60 samples are in the CSV, including the wide NVMe write spread.
  • Client: run from pmox2059, a host with HDD OSDs only. No 4 MB read can be served by a local flash OSD, so every read crosses the network like a real client.
  • Cluster: idle — 109/109 OSDs up and in, every placement group active+clean, zero backfill or recovery for the whole campaign.
  • Network: client traffic uses the Ceph public network (10 GbE, MTU 1500); replication uses the separate 25 GbE cluster network (MTU 9000).
  • TrueNAS: fio runs from the September campaign — sequential and 4 KB random, plus a 70/30 mixed workload, with ARC hit rates recorded per pool.

Read this before quoting a number

rados bench uses a limited queue depth and a single OSD thread per RADOS instance. It underreports NVMe and multi-drive capability, often by 2–4×. Use these figures to compare tiers against each other, not as drive datasheet replacements. And mind the scale of the client: a single 10 GbE client caps 4 MB reads near 1 GB/s no matter how fast the backend is.

Capacity planning is a separate question from throughput: these tiers are measured, but how much usable space the bulk pools actually yield is set by erasure coding, and what ceph df reports as free is set by the fullest OSD. See Ceph capacity and mixed hardware.

1. Ceph — large objects (4 MB)

At 4 MB, the client link is the limit, not the media. Every tier — HDD included — reads at 0.93–1.02 GB/s from a single client, which is what a 10 GbE public network carries after overhead. Those read numbers are a measurement of the client path, not of each tier's ceiling. The 25 GbE fabric is the OSD replication network; seeing the backend's real read capability would take multiple clients, or a client moved onto the 25 GbE network.

What changed since September

  • SSD 4 MB write: 431 → 934 MB/s (2.2×). The ceph_ssd pool went from 32 to 128 PGs and has finished rebalancing.
  • NVMe 4 MB write: 1,175 → 769 MB/s. Repeats were 677 / 769 / 867, so the spread is wide. The P3600s are old and ceph_nvme is about 65% full; treat 769 as a current measurement and the trend as an open follow-up, not a new ceiling.
  • 4 MB reads: ~1,170 → ~1,000 MB/s. Not a regression. The clean run is from a network-only client on a 10 GbE path; September's reads were faster on some runs because the bench node also hosted flash OSDs and served some reads locally.
  • 4 KB reads are not directly comparable. September's 32K–37K IOPS came from a host with local flash OSDs. The November numbers are what a real client sees across the network.

2. Ceph — small objects (4 KB)

Small-object throughput is where the tiers genuinely differ, because every operation pays replication and controller overhead. NVMe leads writes, Optane lands between NVMe and SSD, and the HDD tier stays close to the SATA SSD tier thanks to its NVMe write-ahead log.

Hardware is not the only variable

September showed HDDs beating the SATA SSD tier on 4 KB writes (2,299 vs 1,999 IOPS). The clean rerun reverses that (1,324 vs 1,869), because the SSD pool gained PGs and rebalanced while the HDD tier did not. The durable lesson is that small-write ordering depends on pool layout and WAL placement, not just on media — which is exactly why we re-measured before publishing a law.

Why the NVMe write number looks low

6,142 write IOPS is unimpressive for NVMe, and most of it is the harness rather than the drives:

  • 3× replication means each logical write becomes three OSD writes; the raw per-drive figure is roughly three times higher.
  • 16 rados threads is far below the queue depth these drives can sustain (64–128+).
  • The drives are Intel P3600 — PCIe 3.0 enterprise NVMe from 2015. Fast for their generation, not modern Gen 4, and now running in a pool that is about 65% full.
  • The remaining gap is worth chasing: see the NVMe write trend in the follow-ups.

Do not compare 4 KB reads to September

September's 4 KB read figures (32,024 IOPS NVMe, 37,629 SSD) were taken from pmox2064, which also hosts flash OSDs, so a meaningful share of reads were served locally. November ran from a network-only client. The table above is the number a client actually experiences; the September figures measure something else.

3. Optane-backed tier — now characterized

The ceph_optane tier pairs a 3.49 TB SATA SSD with a dedicated 64 GB NVMe partition for the BlueFS DB, with WAL co-located. After the pool was rebuilt and moved to 128 PGs, it now has publishable numbers:

  • 4 MB write: 909 MB/s — essentially the SATA SSD rate, well above the HDD tier.
  • 4 KB write: 4,593 IOPS — about 2.5× the SSD tier, below NVMe's 6,142.
  • 4 KB random read: 22,279 IOPS — within 5% of SSD and above NVMe at this client depth, all network-capped.

The original expectation was a tier between SSD and NVMe: close to NVMe for metadata-heavy work, close to SSD for bulk throughput. That is what the clean run shows. The earlier "pending" status was correct at the time — the configuration was not trustworthy — and it is now retired.

Takeaway

NVMe special vdevs and high ARC hit rates make even HDD pools feel all-flash for reads. Write performance is usually a configuration problem before it is a hardware problem — the Icarus story is the proof.

5. The Icarus tuning story: 375 → 4,271 MiB/s

The daghome pool had 8 SATA SSDs in four mirrors, a 2× NVMe special vdev, a 120 GB Intel NVMe SLOG, and 503 GiB of RAM. Sequential writes should have been measured in gigabytes per second. They measured 375 MiB/s.

Bottleneck 1: special_small_blocks=128K with recordsize=16K

The special vdev is meant for metadata and small-file data. The threshold was set to 128 KB, but the dataset's recordsize was 16 KB. Every 16 KB block was therefore diverted to the 2× NVMe special mirror. The 8 SATA SSDs sat idle for writes while the metadata accelerator became the main write path.

Fix: special_small_blocks=0. Metadata stays on NVMe; data spreads across the main pool. Result: 375 → 478 MiB/s (+27%).

Bottleneck 2: logbias=latency

This forces every write — including asynchronous writes that should aggregate in RAM — through the ZIL/SLOG. The SLOG was a single 120 GB NVMe with roughly 360 MB/s of sequential write throughput, so it imposed a hard ceiling below what the main pool could do.

Fix: logbias=throughput. Async writes bypass the ZIL. Result: 375 → 524 MiB/s (+40% cumulative).

Bottleneck 3: zfs_dirty_data_max=4 GB

OpenZFS traditionally defaults this to about 10% of RAM — roughly 50 GB here. TrueNAS SCALE ships a hard-coded 4 GB, inherited from appliance-era defaults. With 503 GiB of RAM and a 4 GB cap, the transaction group throttle engaged every few seconds and blocked writes that the SSDs could easily absorb.

Fix: raise it to 32 GB (about 6% of RAM; 10–20% is reasonable for write-heavy pools). Result: 524 → 4,271 MiB/s (+1,039% cumulative). The NFS-like psync workload reached 1,549 MiB/s, enough to saturate 25 GbE.

Eleven times faster with no hardware changes

Three settings. No new drives, no new controller, no rebuild. The pool was not slow; it was configured to be slow. This is the single most reusable lesson on the site.

6. Lessons and caveats

Reads hit the client link first

Across HDD, SSD, NVMe, and Optane, 4 MB reads landed at 0.93–1.02 GB/s. From one client on 10 GbE, that is the network, not the media. Raise the client path — more clients, or public traffic on the 25 GbE fabric — before buying faster drives.

BlueFS offload keeps HDDs close

Putting WAL on NVMe took the bulk tier to 529 MB/s on 4 MB writes and 1,324 IOPS on 4 KB writes — 57% and 71% of the SATA SSD tier, from spinning disks. It is the difference between "HDD is for cold data" and a usable general-purpose tier.

Same client, or it is not a comparison

September's 4 KB reads came from a host that also served some reads from local flash OSDs. Moving to a network-only client lowered the IOPS but made the number honest. Benchmark the path a real client uses.

Benchmark scripts lie

The original harness parsed "IOPS:" while rados bench prints "Average IOPS:"; every value was silently wrong for weeks. Separately, Ceph 19.2.7 rejects -b on seq/rand. Validate the harness before trusting a trend.

What we would do differently

  1. Put the client-facing Ceph public network on the 25 GbE fabric too (and MTU 9000 end to end). Today the public network is 10 GbE at MTU 1500 while replication is 25 GbE at MTU 9000, so a single-client benchmark cannot see the backend ceiling.
  2. Chase the NVMe write trend: 769 MB/s idle versus 1,175 in September. Check P3600 wear and SMART, pool fullness (~65%), and primary-OSD balance.
  3. Benchmark NVMe with realistic queue depth via rbd map or multi-instance fio, not just 16-thread rados bench.
  4. Standardize MTU 9000 on every Ceph path; mixed-MTU links are hard to diagnose and quietly expensive.
  5. Characterize a new tier before putting production data on it — the Optane tier is now done.

Reproduce it

# 4 MB large-object test
rados -p <pool> bench 30 write -b 4194304 -t 16 --no-cleanup
rados -p <pool> bench 30 seq  -t 16
rados -p <pool> bench 30 rand -t 16

# 4 KB small-object test
rados -p <pool> bench 30 write -b 4096 -t 16 --no-cleanup
rados -p <pool> bench 30 rand -t 16

# clean up that run (objects are benchmark_data_<host>_<pid>_objectN)
rados -p <pool> ls | grep benchmark_data_<host>_<pid>
rados -p <pool> cleanup --prefix benchmark_data_<host>_<pid>

On Ceph Squid 19.2.7, -b is accepted only by write; seq and rand read the objects the write left behind. --run-name is accepted but ignored on this build, so clean by the actual benchmark_data_<host>_<pid> prefix. A 30-second 4 KB write leaves hundreds of thousands of objects and cleanup is not instant. Run the client on a host whose OSDs are of a different class than the pool under test, or local reads will inflate the result.
