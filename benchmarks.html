Benchmarks

The most useful thing about a heterogeneous cluster is that you can measure what each kind of hardware actually does under the same workload. These are production numbers, not clean-room numbers: 3× replication, live cluster, September 2026.

Methodology

  • Ceph: rados bench, 30 seconds per test, 16 concurrent threads, 3× replication (size 3, min_size 2), MTU 9000 on the storage fabric, run from a monitor node against dedicated profile pools.
  • TrueNAS: fio runs against each pool, sequential and 4 KB random, plus a 70/30 mixed workload. ARC hit rates recorded per pool.
  • Both: results reflect a real cluster doing real work. Background scrub, backup traffic, and other tenants can move the numbers by 10–20%.

Read this before quoting a number

rados bench uses a limited queue depth and a single OSD thread per RADOS instance. It underreports NVMe and multi-drive capability, often by 2–4×. Use these figures to compare tiers against each other, not as drive datasheet replacements. The NVMe write number in particular is a benchmark-harness ceiling, not a drive ceiling.

1. Ceph — large objects (4 MB)

At 4 MB, the network is usually the limit, not the media. Both SSD and NVMe reads land at roughly 1,170 MB/s, which is what a 25 GbE link can carry after overhead. The HDD tier's 852 MB/s read is the interesting result: spinning rust with NVMe WAL/DB offload is not the bottleneck people expect.

Random and sequential reads were effectively identical at 4 MB. With three replicas placed across OSDs by CRUSH, a 4 MB object is large enough that seek behavior stops mattering; throughput is set by the network and the slowest replica.

Write throughput separates the tiers more honestly: NVMe writes at 2.7× the SATA SSD rate, and the HDD tier reaches about 80% of the SSD rate. That last figure is entirely due to BlueFS WAL offload.

2. Ceph — small objects (4 KB)

This is the test that reveals real differences. Small-object IOPS are dominated by seek time, controller overhead, and whether metadata operations land on flash.

HDD write IOPS beat SATA SSD write IOPS

The HDD tier reached 2,299 4 KB write IOPS against 1,999 for the plain SATA SSD tier. The NVMe WAL absorbs the small writes and commits them asynchronously, so the rotating media no longer pays the seek penalty for each one. Reads still favor SSD (37,629 vs 23,988 IOPS), but the gap is far smaller than the hardware suggests.

Why the NVMe write number looks low

8,320 write IOPS is unimpressive for NVMe, and it is a harness artifact rather than a drive limit:

  • 3× replication means each logical write becomes three OSD writes; the raw per-drive figure is roughly 25,000 IOPS.
  • 16 rados threads is far below the queue depth these drives can sustain (64–128+).
  • 32 PGs across 8 OSDs limits parallelism; 128–256 PGs would distribute load better.
  • The drives are Intel P3600 — PCIe 3.0 enterprise NVMe from 2015, rated around 2,600 MB/s sequential and 460K random-read IOPS at QD128. Fast for their generation, not modern Gen 4.

3. Optane-backed tier — pending

No published numbers yet

The ceph_optane tier pairs a 3.49 TB SATA SSD with a dedicated 64 GB NVMe partition for BlueFS DB. Early benchmark runs exposed configuration problems that skewed the results, so the pool is being rebuilt before it is characterized. The expectation is a tier between SSD and NVMe: close to NVMe for metadata-heavy work, close to SSD for bulk throughput. We would rather publish nothing than publish a number we do not trust.

Takeaway

NVMe special vdevs and high ARC hit rates make even HDD pools feel all-flash for reads. Write performance is usually a configuration problem before it is a hardware problem — the Icarus story is the proof.

5. The Icarus tuning story: 375 → 4,271 MiB/s

The daghome pool had 8 SATA SSDs in four mirrors, a 2× NVMe special vdev, a 120 GB Intel NVMe SLOG, and 503 GiB of RAM. Sequential writes should have been measured in gigabytes per second. They measured 375 MiB/s.

Bottleneck 1: special_small_blocks=128K with recordsize=16K

The special vdev is meant for metadata and small-file data. The threshold was set to 128 KB, but the dataset's recordsize was 16 KB. Every 16 KB block was therefore diverted to the 2× NVMe special mirror. The 8 SATA SSDs sat idle for writes while the metadata accelerator became the main write path.

Fix: special_small_blocks=0. Metadata stays on NVMe; data spreads across the main pool. Result: 375 → 478 MiB/s (+27%).

Bottleneck 2: logbias=latency

This forces every write — including asynchronous writes that should aggregate in RAM — through the ZIL/SLOG. The SLOG was a single 120 GB NVMe with roughly 360 MB/s of sequential write throughput, so it imposed a hard ceiling below what the main pool could do.

Fix: logbias=throughput. Async writes bypass the ZIL. Result: 375 → 524 MiB/s (+40% cumulative).

Bottleneck 3: zfs_dirty_data_max=4 GB

OpenZFS traditionally defaults this to about 10% of RAM — roughly 50 GB here. TrueNAS SCALE ships a hard-coded 4 GB, inherited from appliance-era defaults. With 503 GiB of RAM and a 4 GB cap, the transaction group throttle engaged every few seconds and blocked writes that the SSDs could easily absorb.

Fix: raise it to 32 GB (about 6% of RAM; 10–20% is reasonable for write-heavy pools). Result: 524 → 4,271 MiB/s (+1,039% cumulative). The NFS-like psync workload reached 1,549 MiB/s, enough to saturate 25 GbE.

Eleven times faster with no hardware changes

Three settings. No new drives, no new controller, no rebuild. The pool was not slow; it was configured to be slow. This is the single most reusable lesson on the site.

6. Lessons and caveats

MTU 9000 is not optional

Jumbo frames on the storage fabric produced roughly a 10× gain in some small-block tests. With 9,000-byte frames a 4 MB write is ~290 frames instead of ~2,800. One misconfigured switch port can undo it for the whole tier.

BlueFS offload is a force multiplier

Putting WAL (and sometimes DB) on NVMe makes HDDs competitive for small writes. It is the difference between "spinning rust is for cold data" and 2,299 write IOPS.

Benchmark scripts lie

The automated harness parsed "IOPS:" while rados bench prints "Average IOPS:". Every reported IOPS value was silently wrong for weeks. Manual runs exposed it and told a much better story.

Test the real access pattern

direct=1 bypasses the page cache; psync approximates NFS. The two can differ by 3×. Benchmark the workload you actually serve, not the one that produces the prettiest chart.

What we would do differently

  1. Raise PG counts on the NVMe pools (128–256 instead of 32) to improve small-object parallelism.
  2. Benchmark NVMe with realistic queue depth via rbd map or multi-instance fio, not just 16-thread rados bench.
  3. Standardize MTU 9000 on every Ceph path; mixed-MTU links are hard to diagnose and quietly expensive.
  4. Validate the benchmark harness before trusting months of results.
  5. Characterize a new tier before putting production data on it (see the Optane tier).

Reproduce it

# 4 MB large-object test
rados -p <pool> bench 30 write -b 4194304 --no-cleanup
rados -p <pool> bench 30 seq -b 4194304
rados -p <pool> bench 30 rand -b 4194304

# 4 KB small-object test
rados -p <pool> bench 30 write -b 4096 --no-cleanup
rados -p <pool> bench 30 rand -b 4096

rados -p <pool> cleanup

Always clean up the benchmark objects when you are done.
